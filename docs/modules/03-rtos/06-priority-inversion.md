# 3.6 优先级反转、死锁与饥饿

> 本节目标：理解 RTOS 中“高优先级任务反而不响应”的原因，掌握优先级继承、锁顺序和超时设计。

## 优先级反转

场景：

1. 低优先级任务 L 获取互斥量。
2. 高优先级任务 H 需要同一互斥量，进入阻塞。
3. 中优先级任务 M 就绪并抢占 L。
4. L 无法运行，H 继续等待，M 却持续占用 CPU。

结果是高优先级任务被中优先级任务间接阻塞。

## 优先级继承

FreeRTOS 的互斥量（mutex）支持优先级继承：当 H 等待 L 持有的互斥量时，L 临时提升到 H 的优先级，尽快释放锁。

```c
SemaphoreHandle_t lock = xSemaphoreCreateMutex();
```

注意：二值信号量不提供优先级继承。保护共享资源必须用互斥量，而不是“看起来差不多”的二值信号量。

## 死锁

两个任务互相等待对方持有的锁：

```text
任务 A: 获取 lock1 -> 等待 lock2
任务 B: 获取 lock2 -> 等待 lock1
```

避免策略：

- 所有任务按相同顺序获取锁。
- 尽量缩短持锁时间。
- 使用超时，失败后释放已持有的锁并重试。
- 能用单个锁保护就不要拆成多个交叉锁。

```c
if (xSemaphoreTake(lock1, timeout) != pdTRUE) return ERR_TIMEOUT;
if (xSemaphoreTake(lock2, timeout) != pdTRUE) {
    xSemaphoreGive(lock1);
    return ERR_TIMEOUT;
}
```

## 饥饿

高优先级任务持续运行或频繁唤醒，低优先级任务永远得不到 CPU。

解决方法：

- 高优先级任务必须阻塞等待事件，不能忙等。
- 控制中断和任务频率。
- 为低优先级任务留出预算。
- 使用优先级老化或公平调度（取决于系统）。

## 持锁期间不要做这些事

- 阻塞等待网络。
- 打印大量日志。
- 调用 `vTaskDelay`。
- 等待另一个不确定的锁。
- 执行长计算。

## 常见坑

- 用二值信号量保护共享资源，失去优先级继承。
- 获取锁后忘记释放。
- 在回调或错误路径中提前 return。
- 嵌套锁顺序不一致。
- 所有等待都用 `portMAX_DELAY`，死锁时无法恢复。

## 动手实验

1. 构造 L/M/H 三个任务，复现优先级反转。
2. 把二值信号量换成互斥量，观察 H 的等待时间。
3. 构造两个任务交叉加锁，复现死锁。
4. 用超时和统一锁顺序修复。
5. 记录每个任务的等待时间和持锁时间。

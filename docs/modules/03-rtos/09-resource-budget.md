# 3.9 资源与性能预算

> 本节目标：建立 CPU、内存、栈、延迟和功耗的预算表，并能在开发板上测量。

## 为什么需要预算

“现在能跑”不等于“量产能跑”。传感器最慢响应、网络重连、日志堆积、低温电池内阻变化，都可能把系统推到边界。

预算要回答：

- CPU 最坏占用率是多少？
- 哪个任务栈最危险？
- 一次端到端延迟的上限是多少？
- Flash/SRAM 还剩多少？
- 峰值电流和平均功耗是多少？

## CPU 占用率

FreeRTOS 可以启用运行时统计：

```c
#define configGENERATE_RUN_TIME_STATS 1
#define configUSE_TRACE_FACILITY 1
#define configUSE_STATS_FORMATTING_FUNCTIONS 1
```

实现高精度计数源，然后调用：

```c
TaskStatus_t status[16];
uint32_t total_runtime;
UBaseType_t count = uxTaskGetSystemState(status, 16, &total_runtime);
```

也可以用一个最高优先级空闲钩子统计空闲时间。原则是：**测量最坏场景**，而不是空载平均值。

## 栈预算

```c
UBaseType_t left = uxTaskGetStackHighWaterMark(task);
size_t used_bytes = (stack_words - left) * sizeof(StackType_t);
```

记录每个任务的最小剩余栈，给最坏调用链留 20–30% 余量。中断嵌套和浮点格式化要单独评估。

## 延迟与抖动

端到端延迟要从事件源算到最终动作：

```text
传感器采样 -> 队列 -> 处理任务 -> 通信任务 -> 网络发送
```

测量方法：

- GPIO 翻转 + 逻辑分析仪。
- 高精度计时器打点。
- 串口输出时间戳。
- RTOS trace 工具。

关注平均值没有意义，重点看 P99、最坏值和抖动。

## 资源预算表

| 资源 | 预算 | 实测最坏 | 余量 |
| --- | ---: | ---: | ---: |
| Flash | 400 KB |  |  |
| SRAM | 96 KB |  |  |
| CPU | 70% |  |  |
| 任务栈 | 8 KB |  |  |
| 端到端延迟 | 200 ms |  |  |
| 峰值电流 | 150 mA |  |  |

余量不是浪费，而是为异常、日志、重连和未来需求留的空间。

## 性能问题排查顺序

1. 是否在中断或高优先级任务中做了重活。
2. 是否有忙等、无超时轮询。
3. 是否频繁动态分配/释放。
4. 是否日志输出阻塞。
5. 是否通信重试过于频繁。
6. 是否栈太小导致异常。
7. 是否 Flash 擦写或 DMA 抢占总线。

## 常见坑

- 只测空载 CPU 占用。
- 用平均值掩盖最坏延迟。
- 任务栈按“能启动”配置。
- 日志和统计本身消耗大量 CPU。
- 没有记录版本间的资源变化。

## 动手实验

1. 启用运行时统计，记录每个任务 CPU 占用。
2. 打印所有任务栈高水位。
3. 用 GPIO 打点测量采集到显示的端到端延迟。
4. 人为让网络重连，观察 CPU 和队列积压。
5. 填写完整资源预算表，标出最危险的 3 项。

## 检查清单

- [ ] 能测量 CPU 占用和任务栈。
- [ ] 关注最坏延迟而不是平均值。
- [ ] 有 Flash/SRAM/栈/功耗预算表。
- [ ] 知道日志和统计也会消耗资源。
- [ ] 每个版本都记录资源变化。

# 4.1 串行通信与网络通信

> 本节目标：理解嵌入式设备从板级串口到互联网的通信链路，知道每一层各自解决什么问题。

## 一条典型链路

```mermaid
flowchart LR
  S[传感器] -->|I2C/SPI| M[MCU]
  M -->|UART| W[Wi-Fi 模组]
  W -->|TCP/TLS| G[网关/云]
  G -->|MQTT| D[Web 仪表盘]
```

每一层都有自己的帧格式、错误处理、超时和重试。上层不能假设下层永远可靠。

![嵌入式 IoT 协议分层与逐层封装：MQTT、TLS、TCP、IP、Wi-Fi 与 UART](/images/iot-protocol-stack.svg)

*图：发送时逐层加头，接收时逐层剥离；任何一层的超时都会表现为上层“没有响应”。*

## 串行通信的特点

- 通常点对点、距离短。
- 低层协议简单，但需要自己定义消息边界。
- 没有连接概念，设备可能一直在线，也可能随时掉线。
- 错误类型包括帧错误、校验错误、超时和缓冲区溢出。

UART 只负责搬运字节，不保证：

- 一次读取就是一个完整业务消息。
- 消息按业务顺序到达。
- 对方一定收到。
- 数据一定正确。

## 网络通信的特点

TCP 提供有序、可靠、面向连接的字节流，但：

- 仍然是字节流，没有消息边界。
- 连接可能断开、重连、半开。
- 需要应用层协议定义消息格式。
- TLS 增加握手、证书和时钟要求。

UDP 不保证可靠和顺序，但延迟低，适合实时音视频、部分传感数据。

## 消息边界

常见分帧方式：

| 方式 | 示例 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定长度 | 每帧 16 字节 | 解析简单 | 不灵活 |
| 分隔符 | `\n`、`0x7E` | 易读 | 数据需转义 |
| 长度字段 | `LEN + PAYLOAD + CRC` | 通用 | 需限制最大长度 |
| 连接关闭 | HTTP/1.0 | 简单 | 连接开销大 |

嵌入式协议最常用“帧头 + 长度 + 负载 + 校验”。

## 可靠性不是一层的事

```text
应用层：消息 ID、ACK、重试、去重
传输层：TCP 重传、排序
链路层：CRC、帧同步
物理层：电平、时序、抗干扰
```

即使使用 TCP，也需要应用层处理业务超时、幂等和离线缓存。设备断网时，TCP 连接可能不会立刻报错，必须用心跳和超时检测。

## 延迟与吞吐

- UART 115200 8N1 约 11.5 KB/s 理论吞吐。
- Wi-Fi 受信号、重传、功耗策略影响。
- MQTT 的 QoS 和 TLS 会增加延迟与内存开销。
- 设备端要限制单次消息大小，避免阻塞和内存峰值。

## 常用诊断

- 串口日志：看解析、重连、错误码。
- 逻辑分析仪：看 UART/I2C/SPI 原始波形。
- `ping`/`tcpdump`：看网络可达性和包。
- Broker 日志：看连接、订阅、QoS。
- 设备端指标：重连次数、发送队列长度、丢弃计数。

## 前端类比

WebSocket 也不是“每帧一个业务消息”，仍然需要协议字段。设备端 MQTT 更像浏览器里的 WebSocket + 消息队列，但网络更不稳定、内存更小、时钟可能不准。

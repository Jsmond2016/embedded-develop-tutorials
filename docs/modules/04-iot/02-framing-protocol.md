# 4.2 帧设计、校验与可靠性

> 本节目标：设计一套简单但可靠的二进制协议，覆盖帧同步、长度、校验、序号、ACK、重试和去重。

## 推荐帧格式

```text
SOF(2) | VER(1) | TYPE(1) | SEQ(1) | LEN(2) | PAYLOAD(0..N) | CRC16(2)
```

- `SOF`：帧头，例如 `0xAA 0x55`。
- `VER`：协议版本，便于升级。
- `TYPE`：消息类型。
- `SEQ`：序号，用于 ACK、去重和乱序检测。
- `LEN`：负载长度，必须限制最大值。
- `CRC16`：覆盖版本、类型、序号、长度和负载。

不要只校验负载，否则长度和类型被篡改也无法发现。

## CRC8 示例

```c
static uint8_t crc8_atm(uint8_t crc, uint8_t data)
{
    crc ^= data;
    for (uint8_t i = 0; i < 8; ++i) {
        crc = (crc & 0x80U) ? (uint8_t)((crc << 1) ^ 0x07U) : (uint8_t)(crc << 1);
    }
    return crc;
}

static uint8_t frame_crc8(const uint8_t *data, size_t len)
{
    uint8_t crc = 0;
    for (size_t i = 0; i < len; ++i) {
        crc = crc8_atm(crc, data[i]);
    }
    return crc;
}
```

CRC 不是加密，只用于检测传输错误。需要防篡改时使用 MAC/签名。

## 解析器状态机

```c
typedef enum {
    RX_SOF1,
    RX_SOF2,
    RX_HEADER,
    RX_PAYLOAD,
    RX_CRC
} rx_state_t;
```

每个字节推进状态。收到超长长度、非法版本或 CRC 错误时，丢弃当前帧并重新寻找 SOF。

## 可靠性机制

### ACK 与重试

```text
发送方: DATA(seq=n) -> 启动超时
接收方: 校验通过 -> ACK(seq=n)
发送方: 收到 ACK -> 完成
        超时 -> 重发 DATA(seq=n)
```

重试必须有限次，超过阈值上报错误，不能无限重发。

### 去重

接收方记录最近处理过的 `seq`，重复帧只回 ACK，不再执行业务。否则“传感器上报”可能变成两次。

### 幂等

命令设计尽量幂等，例如“设置间隔为 1000 ms”比“增加 1 秒”更适合重试。

## 背压与队列

- 发送队列满时返回 `ERR_NO_SPACE`。
- 重要消息优先，可丢弃低优先级日志。
- 限制单帧最大长度，避免大消息撑爆缓冲区。
- 接收队列溢出要计数并暴露到指标。

## 版本兼容

- 保留 `VER` 字段。
- 新增字段时放在末尾，并带长度。
- 未知 `TYPE` 返回“不支持”，不要直接崩溃。
- 协议文档和测试用例一起版本化。

## 常见坑

- 只使用分隔符，但负载中可能出现同样字节。
- 长度字段无上限，恶意帧导致内存耗尽。
- CRC 计算范围不一致。
- 重试没有去重，业务重复执行。
- 协议升级不兼容旧设备。

## 动手实验

1. 实现帧编码器和解码器。
2. 构造随机字节流，确保解析器不越界、不崩溃。
3. 注入丢包、重复包、乱序包，验证 ACK 和去重。
4. 把最大帧长从 64 改到 1024，评估 RAM 影响。
5. 写协议文档，包含字节序、字段表和错误码。
